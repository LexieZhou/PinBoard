⏺ 提取位置的方式

  这个文件用的是 TritonAI LLM API（UCSD的AI服务，底层是 api-gpt-oss-120b
  模型），不是 Google Maps API。

  流程：
  1. 把页面文字（最多12000字符）和页面标题拼成 prompt
  2. 发给 TritonAI 的 /chat/completions 接口
  3. LLM 根据 system prompt 的规则，从文本中识别具体地点，返回 JSON

  ---
  Regex 的作用

  文件里有两处正则：

  1. stripCodeFence（第91行）
  s.match(/^```(?:json)?\s*([\s\S]*?)\s*```$/)
  LLM 有时会把 JSON 包在 markdown 代码块里（如 ```json {...} 
  ```），这个正则把代码块外壳去掉，只保留里面的内容。

  2. parsePlacesJson 里的 fallback（第63行）
  jsonText.match(/\{[\s\S]*\}/)
  如果第一次 JSON.parse 失败（LLM 返回了带额外文字的内容，比如 "Here is the 
  result: {...}"），这个正则从字符串里找最外层的 {...} 块，再尝试一次
  parse。这是一个对 LLM 输出不稳定的容错处理。

  ---
  总结：整个提取完全依赖 LLM 的语义理解，没有用到 Google Maps。Google Maps
  可能在其他文件（如地理编码/显示地图）里用到。

⏺ Google Maps 用在以下两个地方：

  ---
  src/lib/places.ts — 核心调用

  使用的是 Google Places API (New) Text Search，端点
  https://places.googleapis.com/v1/places:searchText。

  流程：LLM 提取出地点名称后，这里负责把名称转成真实坐标：
  - geocodeOne：对单个地点发请求，用地点名+上下文拼成 textQuery，拿回
  placeId、address、lat/lng
  - geocodeMany：循环调用 geocodeOne，把所有提取到的地点都地理编码，失败的跳过

  ---
  src/background/service-worker.ts（第2、62行）

  在 service worker 里调用 geocodeMany，拿到带坐标的位置列表后转成 Pin
  数据，用于地图展示。

  ---
  整体流程总结：

  页面文字 → TritonAI LLM → 地点名称列表
                                    ↓
                       Google Places Text Search API
                                    ↓
                           lat/lng + placeId → 地图 Pin

⏺ 可以从三个可能的失败点入手：

  ---
  潜在的丢失点

  1. 文本截断（triton.ts:28）：只取页面前 12000
  字符，长页面后半段的地址会被直接丢弃
  2. LLM 漏提：模型可能没识别到某些地点，或者 system prompt 的规则把它们过滤掉了
  3. Geocoding 静默失败（places.ts:63）：geocodeOne 返回 null 时只打
  console.warn，直接跳过，不会报错
